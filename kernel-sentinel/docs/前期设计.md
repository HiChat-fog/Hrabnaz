# 内核哨兵前期设计

## 项目定位与意义

内核哨兵是基于eBPF的内核级终端威胁检测与行为观测系统。当前主流终端安全工具（Falco、Tetragon、Tracee）的感知层在用户态：通过系统日志或内核模块获取事件后，再在用户态做规则匹配。这种架构有两个固有缺陷。一是延迟：用户态从内核到规则引擎的路径至少经过三次上下文切换和一次数据拷贝，攻击者可以利用这个窗口完成操作后退出。二是盲区：用户态无法观测内核内部行为，例如进程树拓扑变化、TCP流状态转换、操作频率偏离，这些信息必须由内核空间实时维护才完整。内核哨兵将感知探针植入内核关键路径，在内核空间维护进程树拓扑图和TCP流状态机，并实时用推理引擎评估风险分，纳秒级完成威胁判别。这使系统能检测用户态工具漏检的攻击模式：fork风险继承、C2心跳流、勒索软件批量操作序列、DNS隧道高频偏离。项目同时面向两个方向：方向一（网络安全与攻防技术）为公安终端提供零依赖静默部署的威胁检测能力；方向五（智慧教学）为信息安全课程提供内核行为可视化与攻击链回放教学工具。

## 整体架构与设计依据

系统采用四层纵深架构。第一层内核探针层由16组eBPF程序组成，覆盖系统调用（raw_syscalls/sys_enter与sys_exit两个tracepoint）、VFS层（vfs_open、vfs_write、vfs_unlink三个kprobe）、网络栈（tcp_v4_connect、tcp_v6_connect、udp_sendmsg、tcp_set_state、tcp_sendmsg五个kprobe）、进程调度（sched_process_fork、sched_process_exec、sched_process_exit三个tracepoint）、安全扩展（commit_creds、do_init_module、security_bpf_prog_free三个kprobe，event_type 80-82）。选择tracepoint+kprobe混合而非纯kprobe的依据是：tracepoint有稳定的内核ABI保证跨版本兼容，kprobe能挂载内核内部函数（如tcp_v4_connect）获取sock结构体内部字段，两者互补覆盖了 syscall→VFS→网络栈→进程调度四条数据产生路径。第二层内核推理层在探针捕获事件后即时评估风险：维护LRU Hash Map（4096条，pid→累计风险分0-100）做四维推理——敏感文件访问（手动展开字符比较匹配/etc/shadow等路径，/etc/shadow与/etc/sudoers各加40分、/etc/gshadow加35分、/root/.ssh加30分）、可疑网络连接（恶意端口加50分、高位非标端口加10分、重复建连加5分、白名单IP跳过风险累加避免误报）、批量文件操作（写删重命名各加2分）、进程注入（ptrace加35分、kill信号加20分）。风险分阈值设计为enforce模式≥70阻断、≥40标记高风险，依据MITRE ATT&CK中高危攻击（反弹Shell、勒索软件、rootkit）的复合行为特征——这些攻击至少触发两个推理维度，总分轻松超过40。推理引擎返回值分三级（0正常、1触发告警、2需阻断），各探针根据返回值决定是否提交ring buffer（注：阻断需 KS_ENFORCE=1 + 干跑期已过 + 非保护名单，默认 monitor 只告警不杀）。选择0-100整数范围而非浮点是因为eBPF验证器不允许浮点运算，且整数粒度足够区分高/中/低风险。第三层用户态引擎层包含六个独立模块：事件聚合器、规则引擎、跨事件关联引擎、统计基线偏离检测、攻击链还原、取证日志。聚合器从ring buffer消费二进制数据，经两阶段越界保护（先校验EventHeader 64字节，再按event_type校验完整结构体832/336/112/72字节）解码为DecodedEvent。规则引擎用YAML定义检测条件，Field枚举保证字段名在反序列化时校验，拼写错误的field不会静默返回false。跨事件关联引擎弥补规则引擎只能匹配单条事件的缺陷，实现了三种关联类型：窗口关联（时间窗口内A+B事件同时出现）、序列检测（按顺序出现的步骤，如勒索软件的读→加密写→删）、进程树关联（同进程树中不同进程行为组合）。统计基线偏离检测为每个进程建立六维行为基线（syscall、file_ops、net_ops、dns_ops、ptrace、signal各60秒窗口的平均值与标准差），用z-score偏离检测替代硬编码阈值——wget高频网络是正常的，bash高频网络是异常的，z-score自适应这种差异。攻击链还原将同一进程的离散告警按MITRE ATT&CK阶段分类串联为攻击叙事。取证日志用SHA-256哈希链保证日志防篡改，修改任意一条记录会导致所有后续记录的hash校验失败。第四层CLI交互层通过命令行提供进程树视图、事件时间线、系统调用回放和攻击链可视化，支持攻击场景模拟与实时检测演示。

选择eBPF而非内核模块（ADR-001）的依据：eBPF验证器保证程序不会panic或越界访问，运行时安全；BPF CO-RE机制一次编译跨内核版本运行，无需为每个内核版本单独编译；动态加载卸载不需重启系统，部署风险低。不利面是验证器限制（100万指令上限、8级调用深度（5.2+，早期4-5级）、512字节栈、禁止浮点和无界循环），这使推理引擎的手动字符串比较必须展开为固定次数的字符逐个比对而非循环。选择Rust而非C/Python（ADR-002）做用户态引擎：编译期内存安全无数据竞争、零开销抽象无GC适合高频事件处理、aya-rs提供类型安全的BPF程序生命周期管理。选择ring buffer而非perf buffer（ADR-003）：modern tier 用 ring buffer（全局缓冲区，事件有序无需按CPU合并），legacy/ancient tier 回退 perf buffer（老内核无 ringbuf helper）——双轨设计兼容 3.10/4.x。

## C/Rust内存对齐与零拷贝传输

内核探针与用户态引擎之间通过ring buffer传递二进制数据，要求C端和Rust端的结构体布局字节级一致。设计采用三项保障措施。第一，所有结构体用#[repr(C)]强制C ABI布局，Rust编译器不会插入隐式padding。第二，在C端和Rust端分别声明显式_pad字段（EventHeader的_pad1[u32]填充event_type后到timestamp_ns的8字节对齐、_pad2[u32]填充syscall_nr后到retval的8字节对齐；NetEvent的_pad3[u8;2]保证整体大小为8字节倍数），使padding意图可见而非依赖编译器隐式行为。第三，Rust侧编译期静态断言验证每个结构体大小：size_of<EventHeader>()必须等于64、ExecEvent 832、FileEvent 336、NetEvent 112、SignalEvent 72，如果C/Rust两侧有任何字段遗漏或对齐不一致，编译期断言就会报错而非运行时数据错乱。

EventHeader的64字节布局逐字段记录了偏移量：event_type(u32)偏移0、_pad1(u32)偏移4、timestamp_ns(u64)偏移8、pid(u32)偏移16、tid(u32)偏移20、uid(u32)偏移24、ppid(u32)偏移28、comm([u8;16])偏移32、syscall_nr(i32)偏移48、_pad2(u32)偏移52、retval(i64)偏移56。NetEvent在header之后依次为saddr(u32偏移64)、daddr(u32偏移68)、sport(u16偏移72)、dport(u16偏移74)、proto(u8偏移76)、family(u8偏移77)、saddr6([u8;16]偏移78)、daddr6([u8;16]偏移94)、_pad3([u8;2]偏移110)。saddr6紧接family无中间填充，因为[u8;16]的alignment是1不需要8字节对齐。聚合器的两阶段越界保护先检查data.len() >= sizeof(EventHeader)读取event_type，再根据event_type检查data.len() >= min_event_size(event_type)，用read_unaligned避免对齐UB。

## 规则引擎与Field枚举类型安全

检测引擎的规则匹配依赖Field枚举做类型安全的字段访问。Field枚举有25个变体（comm、pid、ppid、uid、syscall_nr、filename、args、file_bytes、saddr、daddr、sport、dport、proto、saddr6、daddr6、family、target_pid、signal、module_name、prog_name、source_ns_inum、target_ns_inum、cap_eff、action、event_type），每个变体通过serde rename映射到YAML字段名（⚠️ all_yaml_names() 返回 24 项不含 event_type，已知不一致）。YAML规则加载时，serde_yaml反序列化会校验field值是否在枚举范围内——如果规则写了field: xyz（拼写错误或不存在），加载会直接返回Err而非静默返回false。这解决了传统规则引擎的一个典型问题：规则作者写了错误的字段名，引擎不报错只返回"不匹配"，攻击者绕过检测而运维人员不知道规则失效。

condition_matches函数根据Field变体自动选择匹配策略。13个数值字段（pid、ppid、uid、syscall_nr、sport、dport、target_pid、signal、file_bytes、event_type、source_ns_inum、target_ns_inum、cap_eff）走数值parse再比较，支持Equals/GT/LT/GTE/LTE/NotEquals六种比较操作符；对Regex/Contains/StartsWith操作符，先将数值转为字符串再调用字符串匹配函数，使端口号能用regex匹配（如^(4444|1337|31337)$同时检测多个恶意端口）。12个字符串字段（comm、filename、args、saddr、daddr、proto、saddr6、daddr6、family、module_name、prog_name、action）走字符串原生方法（Equals/Contains/StartsWith）或regex::Regex预编译匹配。IPv6字段（saddr6、daddr6）复用字符串匹配但不建议regex（IPv6地址格式复杂不适合正则），family字段仅支持equals操作符。Operator枚举支持10种操作符（equals、contains、starts_with、regex、gt、lt、gte、lte、not_equals、not_regex），覆盖了安全规则的全部常见匹配需求。

YAML规则集目前9个文件23条规则覆盖9类攻击：反弹Shell（bash -i/nc -e，T1059.004）、勒索软件加密（.encrypted/.locked后缀，T1486）、提权攻击（SUID/sudoers/ptrace/LD_PRELOAD/insmod/cron，T1548.001等）、数据窃取（敏感文件+外连端口，T1041）、DNS隧道（高频UDP查询+可疑域名，T1071.004）、Rootkit（insmod/proc异常/SIGKILL，T1547）、容器逃逸（event_type=80，T1611）、LKM加载（event_type=81，T1547.006）、eBPF篡改（event_type=82，T1070）。

## 跨事件关联引擎

规则引擎只能匹配单条事件，这是根本缺陷。攻击行为本质上是跨事件的：读/etc/shadow后外连10.0.0.1:4444需要两条事件才能检测，但YAML规则的AND条件在同一事件中——daddr和filename不可能出现在同一个事件里。关联引擎弥补这个缺陷，实现三种关联类型。

窗口关联在时间窗口内检查A事件和B事件是否同时出现。数据结构用VecDeque维护近期事件的滑动窗口，每个新事件加入后自动清理超过窗口大小的过期事件。当新事件满足condition_b时，在窗口内搜索满足condition_a的历史事件。置信度计算：基础0.6（窗口关联本身比单事件匹配更可信），同一PID+0.2（同进程关联比跨进程更可信），多次A事件+0.1（模式更强），上限1.0。

序列检测检查同一PID的事件是否按步骤顺序出现，步骤间时间间隔不超过max_gap。核心数据结构是SequenceTracker，以(rule_idx, pid)为键存入HashMap。这里的关键设计决策是键使用(rule_idx, pid)而非仅pid——如果多个序列规则共享同一个pid键，规则A推进tracker到step=2后，规则B（只有2步）看到step=2 >= steps.len()=2会重置tracker，破坏规则A的进度。独立键保证每个序列规则对同一进程有独立的追踪状态。序列完成时tracker自动重置，置信度基础0.7，3秒内完成（快速执行的序列更可疑）额外+0.2。间隔超max_gap时重置tracker并从step 0重新开始。

当前定义8条关联规则：数据窃取（30秒窗口，读取/etc/shadow后外连4444端口，T1041）、SSH密钥窃取（60秒窗口，读取.ssh后外连，T1048）、勒索软件序列（max_gap 10秒，EventType(11)→And(EventType(12), FilenameContains(.encrypted))→EventType(13)，T1486）、反弹Shell（5秒窗口，bash -i后外连，T1059.004）、提权+持久化序列（max_gap 60秒，chmod +s后修改sudoers，T1548.001）、DNS隧道（60秒窗口，重复DNS查询即高频，T1071.004）、sshd→nc 与 cron→wget 进程树关联（TA0001/T1059.004、TA0003/T1053.003）。

## 统计基线偏离检测

传统异常检测用硬编码阈值（"每次可疑操作加2分，总分超过0.7就告警"），这有两个问题。一是固定阈值无法适配进程差异：wget高频网络是正常的，bash高频网络是异常的，固定阈值要么误报wget要么漏报bash。二是阈值靠经验设定没有统计学依据，偏离程度无法量化。

统计基线偏离检测为每个进程维护六维行为基线（syscall、file_ops、net_ops、dns_ops、ptrace、signal），每维记录60秒窗口内的平均值μ和标准差σ。当前窗口的频率值与基线的偏离度用z-score量化：z = (current - μ) / σ。z > 2σ触发低风险偏离，z > 3σ触发中等偏离，z > 5σ触发严重偏离。

基线建立依赖滑动窗口机制。每个进程最多维护20个FreqSnapshot（一个60秒窗口的频率计数），新事件到来时检查与当前窗口开始时间的间隔：间隔 >= 60秒则创建新窗口，间隔 < 60秒则在当前窗口累加计数。这保证每个FreqSnapshot代表一个完整的时间段而非所有事件堆在一个快照里。**2026-08 OOM 修复后**所有进程（包括高频短命进程）统一写入 `freq_history`（max_pids=10000，超限按窗口时间淘汰至 9000，并同步清理 baselines + established_pids）——旧实现只查 baselines 淘汰导致短命进程泄漏，RSS 最高 1.4GB。

基线训练有一个关键设计决策：一次性训练锁定。当进程积累了5个以上已完成窗口（syscall_count > 1表示窗口有实质内容而非刚创建），基线计算完成后pid被加入established_pids集合，之后不再自动重算。原因是：异常检测的基本原则是训练期建立基线、检测期保持基线稳定。如果基线随异常数据持续更新，偏离度会被稀释——进程突然产生500次文件操作后，基线均值从5拉到40，z-score从55降到0.8，告警消失。需要手动调用refresh_baseline()才能重新训练，这模仿了机器学习中的训练-检测分离范式。

在基线未建立前（窗口数 < 5），使用固定阈值作为fallback：syscall 5000次/60秒、file_ops 500次、net_ops 100次、dns_ops 50次、ptrace 3次、signal 10次。这些值基于常见进程行为模式：正常进程通常syscall < 1000、文件操作 < 50、网络操作 < 10。天生高频进程（wget、curl、python、nginx、postgres等18个comm子串）在基线建立前不会被误报，因为它们的正常行为本身就是高频的。

z-score标准差计算使用总体方差（除以N而非N-1），文档中标注了这是近似而非严格的95%置信区间声明——因为参数是从样本估计而非真实分布参数，精确置信区间需要用t分布。对于实战异常检测目的，差异可忽略。

## 内核态进程树追踪与TCP流状态机

这是内核哨兵与Falco/Tetragon拉开差距的核心创新。

Falco在用户态从/proc目录重建进程树——有延迟且不完整（短命进程可能已退出导致/proc无记录）。Tetragon追踪exec事件但不维护实时拓扑图。内核哨兵在内核空间用BPF_MAP_TYPE_LRU_HASH维护pid→process_node的拓扑图（65536条），每次fork更新子进程节点（设计上继承父进程风险分），每次exec更新comm和exe_path，每次exit删除节点释放内存。父进程risk >= 40时子进程自动标记PROC_FLAG_ANOMALOUS。正常fork仅更新Map不发ring buffer减少负载，有异常（风险继承、黑名单进程如systemd→nc）才发事件。进程节点还维护四个标志位：PROC_FLAG_ROOT（uid=0）、PROC_FLAG_CONTAINER（namespace不同）、PROC_FLAG_ORPHAN（父进程已退出）、PROC_FLAG_ANOMALOUS（行为异常）。这是内核空间的实时进程拓扑图，毫秒级更新零延迟。⚠️ 注意：用户态 process_tree.rs 的 risk_score 字段恒为 0（风险分只存在于内核 map，用户态未回灌/继承实现）——"继承父进程风险分"目前是内核侧设计，链路未完全闭环。

TCP流状态机同样在内核空间维护。Falco只检测单个connect事件不追踪流状态。Tetragon有TCP追踪但不在内核空间做状态机推理。内核哨兵在内核空间用net_flows LRU Hash Map（8192条，key为pid+saddr+daddr+sport+dport+proto）追踪每个TCP连接的完整生命周期：SYN_SENT→ESTABLISHED→FIN_WAIT→CLOSED，通过kprobe/tcp_set_state跟踪内核TCP状态转换，kprobe/tcp_sendmsg累计传输字节。在此基础上检测五种异常：C2心跳（同一目标重复连接≥3次，bit0）、数据外传（累计传输>100MB，bit1）、端口扫描（30秒内连接≥20个不同目标，bit2）、长连接（ESTABLISHED持续>24小时，bit3）、快速重连（30秒内断开重连，bit4）。智能发送策略：正常connect只更新Map不发ring buffer，仅异常流和ESTABLISHED/CLOSED里程碑事件发送，减少80%以上的ring buffer负载。

行为频率计数器在内核空间为每个进程维护60秒滚动窗口的六维操作频率（syscall、file、net、dns、ptrace、signal），用freq_counters LRU Hash Map（4096条）。当频率超过阈值时自动标记异常（anomaly_flags 位标志：勒索软件/端口扫描/DNS隧道/暴力破解/注入）。每100次操作定期上报一次频率数据给用户态，仅首次超过阈值时发送告警避免重复上报。窗口过期时重置所有计数器。

智能过滤层（2026-08-30 重构后）实现五级决策：process_whitelist 命中→丢弃、safe_patterns（进程+路径组合白名单）命中→丢弃、风险分 >= 40→放行、freq anomaly_flags 置位→放行、文件 open/read→丢弃且其余事件默认放行。filter_stats_map 用 PERCPU_ARRAY 避免锁争。⚠️ 语义注意：过滤函数命名 `should_send_event` 但返回的 action==1 表示**丢弃**（与直觉相反）；早期"目标过滤率80%"的表述已不适用，现策略为"低风险进程的文件 open/read 恒过滤，exec/connect/signal 等事件照发"。

## SHA-256取证哈希链

取证日志使用SHA-256哈希链保证日志防篡改，满足司法证据链要求。每条JSONL记录包含两个哈希字段：prev_hash链接到前一条记录的hash形成链式依赖，hash是本条记录内容的SHA-256摘要。第一条记录的prev_hash为genesis hash（64个零字符）。

哈希计算的关键细节：prev_hash和hash字段是在hash计算之后添加的——这意味着hash不包含自身和prev_hash，但prev_hash链接到上一条记录的hash（上一条的hash是包含其内容的完整摘要）。修改任意一条记录的内容会改变该记录的hash，进而破坏下一条记录的prev_hash链接，导致所有后续记录校验失败。攻击者无法只修改一条记录而不被检测到，因为必须同时修改所有后续记录的prev_hash和hash，但最后一条记录的hash与外部存储的"最后已知hash"不一致。

序列化确定性是哈希链正确工作的前提。log_event用serde_json::json!宏构建record（IndexMap，插入顺序），然后将record转为BTreeMap（按key字母排序）再序列化计算hash。verify_chain同样将记录转为BTreeMap再序列化重新计算hash。两处统一使用BTreeMap保证key排序一致——如果log_event用IndexMap而verify_chain用BTreeMap，可选字段（如saddr在IndexMap中按插入排但在BTreeMap中按字母排）会导致key顺序不同，verify_chain会假报"链断裂"。日志轮转配置为100MB按大小轮转，归档用gzip压缩（flate2::GzEncoder），30天自动清理过期归档。写入用64KB BufWriter缓冲，每1000条事件自动flush，告警立即flush，进程退出时Drop trait保证最终flush。

## 攻击链还原

攻击链还原将同一进程的离散告警按MITRE ATT&CK十阶段分类串联为攻击叙事，使运维人员看到的是"反弹Shell→凭据窃取→数据外传"的完整攻击过程而非零散告警。十阶段分类用启发式规则：comm含bash且args含-i或/dev/tcp归入InitialAccess（TA0001），filename含/etc/cron或systemd归入Persistence（TA0003），args含chmod +s或LD_PRELOAD归入PrivilegeEscalation（TA0004），filename含/etc/shadow归入CredentialAccess（TA0006），dport为4444等恶意端口归入Exfiltration（TA0010）。同阶段连续事件自动合并到同一个AttackStep（events列表追加不创建新step）。置信度计算：阶段数>=3时基础phase_count × 0.15上限0.8，包含高危阶段（InitialAccess/Exfiltration/PrivilegeEscalation）额外+0.2上限1.0，事件数太少但阶段多（total_events < 3且phase_count >= 3）时置信度乘0.6降低误报。时间窗口300秒，AttackPhase枚举derive了PartialOrd/Ord保证阶段排序（InitialAccess < Execution < Persistence < ... < Exfiltration）。
